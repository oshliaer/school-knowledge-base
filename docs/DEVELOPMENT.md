# Разработка

## Первый запуск

```bash
python -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Команды

| Команда | Описание |
|---------|----------|
| `.venv/bin/python scripts/md2anki.py` | Собрать все Markdown-колоды |
| `.venv/bin/python scripts/md2anki.py "Папка предмета"` | Собрать одну Markdown-колоду (аргумент — путь/имя директории предмета, напр. `"Вероятность и статистика 7-9"`) |
| `.venv/bin/python scripts/md2anki.py --output /tmp/anki` | Указать выходную директорию |
| `.venv/bin/python scripts/fetch_countries.py` | Обновить данные стран из Wikidata (по умолчанию пишет в `География мира/countries.csv`; путь переопределяется флагом `--output`) |
| `.venv/bin/python scripts/fetch_flags.py` | Скачать/обновить флаги в `flags/` и обновить маппинг `flags.csv` (`wikidata_id → *_flag_file`), который затем читает `csv2anki.py` |
| `.venv/bin/python scripts/csv2anki.py` | Собрать CSV-колоды (например, «География мира») |

Результат сборки — `dist/<slug-названия>.apkg`: имя получается из `deck.yaml:name` через `slugify` (строчные латинские буквы и дефисы). Например, «Вероятность и статистика 7-9» → `dist/veroiatnost-i-statistika-7-9.apkg`.

## Формат карточек

YAML frontmatter задаёт тип и теги для всего файла. Карточки разделяются строкой `---` (с пустыми строками вокруг).

Карточки типов `basic` и `basic-reversed` разделяют лицевую и обратную стороны строкой `^^^` (с пустыми строками вокруг). Карточка без `^^^` пропускается при сборке. Для `cloze` разделитель не нужен.

### Basic (вопрос / ответ)

```markdown
---
type: basic
tags: [тег1, тег2]
---

id: 01-тема-slug
## Текст вопроса

^^^

Текст ответа.

---

id: 01-тема-slug2
## Следующий вопрос

^^^

Следующий ответ.
```

### Basic-reversed (двусторонняя)

```markdown
---
type: basic-reversed
tags: [термины]
---

id: 01-тема-slug
## Термин

^^^

Определение термина.
```

Создаёт две карточки: термин→определение и определение→термин.

### Cloze (пропуск в тексте)

```markdown
---
type: cloze
tags: [формулы]
---

Площадь круга равна {{c1::π·r²}}.

---

{{c1::Медиана}} делит упорядоченный ряд пополам.
```

Тип `cloze` определяется автоматически при наличии `{{c1::...}}` в тексте.

Всё, что стоит после `^^^`, попадает в поле **Extra** и показывается на обратной стороне под чертой — туда кладут перевод и пояснение:

```markdown
id: 01-тема-slug
This fun festival {{c1::takes place}} around the end of {{c2::February}}.

^^^

**Перевод.** Этот весёлый праздник проходит в конце февраля.

**Зачем это помнить.** О запланированных событиях говорят `take place`, а не `happen`.
```

Для `cloze` разделитель `^^^` **необязателен** — без него карточка соберётся с пустой Extra.

## Озвучка: `{{tts:...}}`

В любом месте карточки можно поставить маркер `{{tts:фраза}}` — при сборке он превращается в **ссылку** на озвучку этой фразы:

```markdown
## bonfire {{tts:bonfire}}

^^^

**костёр**

*There is a big bonfire.* {{tts:There is a big bonfire.}}
```

Как это работает:

- ссылка ведёт на Google Translate TTS (`translate_tts?...&q=фраза`) — mp3 генерируется на лету;
- **аудио не скачивается и не попадает в `.apkg`** — колода остаётся лёгкой, в репозитории не появляются бинарники;
- в карточке отображается значок 🔊 (класс `tts` — оформляется в `styles.css`), фраза видна во всплывающей подсказке;
- клик открывает звук во внешнем браузере, поэтому **нужен интернет**; без сети карточка остаётся полностью читаемой.

Язык озвучки берётся из `deck.yaml` (`tts_lang`), его можно переопределить во frontmatter конкретного файла:

```yaml
---
type: basic
tts_lang: en
---
```

Значение по умолчанию — `en`. Длина фразы — до ~200 символов (ограничение Google Translate TTS).

## Правила создания карточек

- Каждая карточка должна иметь поле `id:` перед заголовком `##`. Формат: `{номер файла}-{тема}-{slug}` (например, `01-таблицы-что-такое`). Slug, как и имя файла, пишется на русском. Без `id:` Anki теряет прогресс при пересборке.
- Тип `basic` — для понятий и вопросов. Тип `cloze` — для формул и расчётов.
- Если для параграфа нужны разные типы — создавать два файла: `01-тема.md` (basic) и `01-тема-задачи.md` (cloze).
- Имена файлов — на русском языке, без транслитерации (пример: `01-таблицы.md`, не `01-tablitsy.md`).

## deck.yaml

```yaml
id: 1748392650123456   # стабильный ID — не менять после первого импорта в Anki!
name: "Название колоды"
tts_lang: en           # язык озвучки {{tts:...}}, опционально (по умолчанию en)
```

ID генерируется один раз. Если изменить — Anki создаст дубликат колоды.

## CI/CD

Сборка описана в `.github/workflows/build.yml`. Что происходит при разных событиях:

| Событие | Сборка | GitHub Release | Telegram |
|---------|--------|----------------|----------|
| Pull request | не запускается | — | — |
| Push/merge в `master` | да, артефакт `anki-decks` в Actions | нет | нет |
| Push тега `v*` | да, `.apkg` прикрепляются к релизу | да | да |
| Ручной запуск (`workflow_dispatch`) | да, артефакт | нет | нет |

**Версия и релиз — разные вещи.** `VERSION` описывает состояние `master` и может уходить вперёд: версию поднимают, когда накопились изменения, а тег ставят тогда, когда колоды решено опубликовать. Часть версий остаётся без релиза — это нормально, а не расхождение. Пользователи видят только релизы, то есть теги; до появления тега изменения из `master` им недоступны, даже если версия уже поднята.

Merge в `master` даёт только артефакт Actions: он скачивается с логином в GitHub, хранится ограниченное время (по умолчанию 90 дней) и на страницу релизов не попадает.

Чего CI не делает:

- не создаёт и не пушит тег — он ставится вручную, когда решено выпускать релиз;
- не обновляет `VERSION` и `CHANGELOG.md` — их правят руками, и ни один скрипт их не читает: версия без тега сборку не ломает;
- не берёт описание релиза из `CHANGELOG.md` — в релиз идёт автогенерируемый список изменений (`generate_release_notes: true`), а в Telegram уходит название тега и ссылки на файлы колод.

## Выпуск релиза

Релиз — отдельное решение, а не следствие merge в `master`. Порядок, когда такое решение принято:

1. Убедиться, что всё нужное в `master` и сборка зелёная.
2. Проверить `VERSION`: он должен соответствовать тому, что публикуется. Если с прошлого релиза версию ещё не поднимали — поднять сейчас и заодно дописать раздел в `CHANGELOG.md` (по образцу предыдущих: «Добавлено / Изменено / Исправлено»), затем закоммитить: `docs: changelog и версия X.Y.Z`.
3. Поставить аннотированный тег на этот коммит и запушить тег:
   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin master
   git push origin vX.Y.Z
   ```
4. Проверить результат: релиз на странице Releases, все `.apkg` из `dist/` прикреплены, уведомление в Telegram пришло.

Правила:

- тег ставится только на коммит, который уже в `master`;
- в момент релиза имя тега должно совпадать с `VERSION` — иначе непонятно, что именно опубликовано; до релиза `VERSION` может быть больше последнего тега;
- тег не переиспользуется: если релиз собран с ошибкой, выпускается следующая версия, а не перезаписывается старая;
- `dist/` в git не попадает (`.gitignore`) — файлы в релиз кладёт CI.

Проверить, что опубликовано, и насколько версия опережает теги:

```bash
cat VERSION
gh release list
git ls-remote --tags origin | tail -5
```
